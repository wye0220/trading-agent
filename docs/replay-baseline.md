# 回放与基线（阶段 5）

本文说明 `replay`、`baseline` 两个命令，数据切分的登记方式，基线报告里每个数字的口径，以及功效测算的做法和假设。

回放与 `scan` 共用阶段 3 的引擎和 `StrategyProvider`。`src/trading_agent/research/` 只做编排和度量，里面没有信号、风控或成交逻辑。

## 命令

```bash
# 回放一段日期。真实数据要显式允许，且区间不得晚于开发可见截止日。
uv run python -m trading_agent replay --from 2024-01-02 --to 2024-01-31 --allow-real-data

# 冻结基线并出两份报告。全量约需一小时。
uv run python -m trading_agent baseline --allow-real-data --jobs 4

# 只冻结基线、出基线报告，不跑扰动和功效测算。
uv run python -m trading_agent baseline --allow-real-data --skip-power
```

`baseline` 依次做五件事：

1. 登记数据切分。
2. 生成冻结清单，得到 `baseline_id`。
3. 用同样的输入回放两次，比较逐笔交易、逐张订单、逐条决策记录的摘要。
4. 写基线报告。
5. 在开发段上回放预登记的扰动，写功效报告。

清单没有变化时，再次运行直接复用已冻结的结果，只重新生成报告。中断后重跑会接着做：已完成的回放保留，半截的那一次清掉重来。

输出文件都在 `reports/` 下，不进版本控制：

| 文件 | 内容 |
| --- | --- |
| `baseline_<scope>.md` | 基线报告 |
| `baseline_<scope>.json` | 同一份数据的结构化版本 |
| `baseline_trades_<scope>.csv` | 逐笔交易 |
| `baseline_power_<scope>.md` | 功效测算 |
| `baseline_power_<scope>.json` | 功效测算的结构化版本 |

文件名里 scope 的冒号换成下划线，例如 `baseline_pa_brooks_ES_RTH_5m.md`。

## 开发可见截止日

`config/paths.yaml` 的 `dev_visible_through` 是开发数据和保留数据的分界。2026-11-22 确认为 2024-12-31。

- 这一天及之前的 K 线进运行库，用于开发、基线和向前验证。
- 之后的 K 线不进运行库。导入时只记三样：条数、RTH 覆盖的 5 分钟格数、内容摘要。价格不保存。
- 截止日是后来才设的（或往前挪了）时，下一次 `ingest` 会把库里已有的、晚于它的真实 K 线移出：先按同样的方式记下覆盖和摘要，再删掉这些 K 线，以及由它们算出的派生线、交易日状态、参考价位和日内异常。原始文件不动。合成数据不受影响。

内容摘要的算法：每根 K 线取 `sha256("来源|合约|周期|起始时刻|开|高|低|收|量")`，把这些摘要当作 256 位整数，按（来源、合约、周期、交易日）相加取模。结果与顺序无关，所以流式导入时累计出的值和从库里重算的值相同。

**这还不是隔离。** 截止日之后的原始文件仍在数据根目录里，作者身份读得到。本阶段做到的是：运行库里没有这些价格，回放和扫描拒绝越过截止日，胶囊的日期和内容摘要已经登记。真正的隔离要等阶段 8 的独立评测身份；届时用登记的摘要核对它拿到的数据。

## 数据切分

切分登记在 `split_registries` 和 `data_segments` 两张表里。`registry_id` 由登记内容的摘要得出，输入不变时重复登记得到同一个标识。

| 段 | 范围 | 状态 |
| --- | --- | --- |
| 开发段 `DEVELOPMENT` | 数据起点至 `forward_validation_start` 之前 | `OPEN` |
| 向前验证段 `FORWARD_VALIDATION` | `forward_validation_start` 至截止日 | `OPEN` |
| 胶囊 `CAPSULE` | 截止日之后，每 20 个有效交易日一个 | `SEALED` |
| 余量 `REMAINDER` | 尾部不足 20 个有效日的部分 | `SEALED` |

影子期是数据终点之后，尚无数据，不登记。

**有效交易日**：当日实际合约的 RTH 数据完整，且来源质量未降级。截止日之前用 `trading_days` 判定；截止日之后没有派生线，用留在库外的覆盖记录判定（原始线覆盖了全部预期的 RTH 5 分钟格）。无效日留在日期清单里，但不计入 20 日。没有信号、数据完整的日子是有效日。不按收益删除日期。

**默认取用顺序**：1 个胶囊盲筛，紧接其后的 2 个合成一个 40 日确认。登记时只给前三个胶囊标上默认用途，其余待定。解封、分配和退回由阶段 8 的账本管理；本阶段不解封、不读取任何胶囊的价格。

**预热**：数据起点后的前 20 个交易日，回放照跑，但不计入任何度量，因为 ADR 等特征还不可用。

**跨窗口持仓**：不存在。截止强平在 RTH 收盘前平掉全部仓位、撤掉挂单，所以持仓不跨交易日，也就不跨切分窗口。

## 冻结清单

`baseline_id` 由清单内容的摘要得出。清单包含：

- scope、策略家族、策略版本、完整配置及其摘要、已启用形态、所需特征。
- 指标定义（EMA、ATR、ADR 等的周期）。
- 引擎版本、截止强平分钟数、回放激活延迟。
- 风控版本、费用、滑点、纸面手数、研究风险单位。
- 时段、周期、日历版本、换月规则版本、tick 大小和价值。
- 行情清单：起止日、交易日数、条数、摘要。摘要覆盖每个交易日所选来源和实际合约的全部周期、全部 revision，所以任何一根出现新 revision 都会改变 `baseline_id`。
- 切分登记的标识和摘要。
- 代码摘要：策略、引擎、特征、行情背景、时段、合约这些决定回放结果的源文件。
- 提示词摘要和随机种子：都是"无"。回放不调用模型，也没有随机数。

git commit 和工作区是否干净随清单一起保存，但不参与 `baseline_id`：只改报告代码或文档不应该让基线失效。工作区有未提交改动时，基线带 `DIRTY_WORKTREE` 标记。

不同策略家族的 scope 各自有独立的 `baseline_id`、运行和报告，不合并计算。

## 两次运行的一致性

主运行 `base:<baseline_id>` 保留全部明细。校验运行 `verify:<baseline_id>` 跑完算出摘要后删掉明细，只在 `research_runs` 留摘要。

比较三个摘要：交易、订单、决策记录。摘要里不含运行标识、订单号、仓位号和写入时间这些随运行变化的字段。三个都相同，状态为 `FROZEN`；有一个不同，状态为 `NON_DETERMINISTIC`，命令以非零状态退出，这份基线不能作为比较基准。

## 基线报告的口径

所有数字按开发段、向前验证段和合计三栏给出。分母是各段的有效交易日（去掉预热日），零交易日计入。

**机会与成交**

- 覆盖率：有效日 ÷ 该段的交易日。
- 机会数：策略给出 `SETUP_VALID` 的决策条数。
- 成交数：已完结的交易笔数。
- 未成交的订单：到期或被撤的挂单，报告列出原因。

**收益与成本**（固定 1 手）

- 券商费用：`config/risk.yaml` 的每手往返费用。
- 模型滑点成本：止损和截止强平的成交价各让了配置的 tick 数。它已经包含在成交价和毛盈亏里，这里单列出来看量级。
- 净 R／笔：按预登记的研究风险单位换算。另给按各笔初始风险换算的值，只作辅助。
- 净 R／日：全部净 R ÷ 有效日数。
- PF：盈利合计 ÷ 亏损合计。没有亏损交易时写"不可估"。
- 滑点压力：每边再多 1 tick，等于每笔净结果再减 2 tick 的价值。这是直接计算，没有重新回放，因为在成交模型里滑点只影响成交价，不影响是否成交。

**风险**

- 最大回撤：按日累计净值算一个，按逐笔累计算一个。
- MAE／MFE：持仓期间子 K 的高低点相对入场价的最大不利和最大有利幅度。事后度量，不影响任何成交。入场所在的那一根子 K 先后不明，不计入；出场所在的那一根计入全幅，在 1 分钟线下偏差不超过一根 1 分钟线。
- 跳空超计划损失：开盘直接越过止损时，实际出场价比"止损价加配置滑点"更差的部分。
- 只有 5 分钟子 K 的成交：当日没有 1 分钟线，同一根 5 分钟线内的先后无法判定，单独计数。

**分组**

按策略 `decision_metadata` 的分组，键由 `config/research.yaml` 的 `report.group_by` 登记（标签 → 元数据路径）。报告代码不认识任何策略专有字段，换一个策略只要改配置。另有通用分组：品种、时段、合约、年份、出场原因、入场时段、子 K 周期。

**风险规模结果**

对固定 1 手的交易按账户预算重新定手数：手数 = ⌊单笔预算 ÷ 每手计划风险⌋，不超过最大手数和当日剩余额度；不够 1 手的跳过；当日净亏损达到日损上限或止损次数达到上限后，当日其余交易跳过。信号和成交路径与 1 手相同，所以是重算，不是再回放。账户限额没有填写或未批准时，这一栏写"未配置"。

**模拟时效假设**

历史文件没有到达时刻，可用时点按"收盘 + 5 秒"估计。报告给出估计值的占比。回放的决策时点等于信号 K 的可用时点加配置的激活延迟。

## 功效测算

目的：在用掉任何保留数据之前，先弄清 40 日确认能分辨多大的效应。

### 预登记的扰动

`config/research.yaml` 的 `perturbations` 登记了四个代表性扰动，两条轨道各两个：

| 标识 | 轨道 | 改动 |
| --- | --- | --- |
| `A1_block_h1l1` | Track A 剪枝防守 | 去掉 Spike 回调对 `h1l1_block` 的豁免，过滤 H1／L1 |
| `A2_tail_60` | Track A | 尾盘不追单的窗口从 30 分钟加到 60 分钟 |
| `B1_spike_2atr` | Track B 结构扩展 | Spike 最小幅度从 2.5 倍 ATR 放宽到 2.0 倍 |
| `B2_retrace_60` | Track B | ES／MES 回调失效阈值从 75% 改为 60% |

扰动是结构化的配置差异：键路径 → 新值。键必须在策略登记的可改键白名单里（`EVOLVABLE_KEYS`）。白名单之外的有：入场订单类型、每日止损次数、形态的启用开关。扰动只在开发段回放，保留交易和订单，逐条决策只留计数。

**这些扰动只用来估计配对日差的波动和连续日依赖。它们不是候选，结果也不是任何改动能盈利的证据。**

### 做法

1. 开发段逐日的基线净 R、扰动净 R 和两边成交数。零交易日为 0。
2. 每次模拟用循环区块 bootstrap 抽 40 个交易日：区块是连续的交易日，保留连续日依赖。
3. 把配对差平移到设定的真实效应 δ：扰动的每日净 R 统一加上"δ − 观察到的平均差"。
4. 在这个确认窗里再做一次内层区块 bootstrap，求配对差均值在单侧 α 下的置信下界。
5. 按轨道的门槛判定，记下每个条件和联合条件是否通过。
6. 对一组 δ 重复，得到通过率曲线；线性插值出通过率达到 80% 所需的最小真实效应。

单侧 α 是实际分配到每次检验的值：家族 α 除以预登记的正式检验次数（Bonferroni）。

门槛（实验预设）：

| 条件 | Track A | Track B |
| --- | --- | --- |
| 置信界 | 下界 > −0.05 R／日 | 下界 > 0 |
| 平均提升 | 不要求 | ≥ 0.05 R／日 |
| 回撤 | 最大回撤至少改善 10% | 最大回撤增量 ≤ 1 R |
| 滑点压力 | 每边多 1 tick 后候选净结果 > 0 且不劣于基线 | 同左 |
| 最低成交数 | 基线和候选各 ≥ 20 笔 | 同左 |

报告另给两个不含部分条件的通过率（不含回撤条件；只看统计条件），用来看是哪一条在卡。

### 短窗正式资格

每条轨道取它的全部扰动里最低的整体通过率，与规划功效目标 80% 比较：

- Track A 的规划效应是 0（候选与基线真实等效）。
- Track B 的规划效应是 `planning_true_effect_r_per_day`，预设 0.10 R／日。它比门槛 δ 大：真实效应恰好等于 δ 时，"平均提升 ≥ δ"这一条天然只有约一半的通过率。

低于目标、输入是合成数据、或开发段有效日太少，资格都是 `EVIDENCE_INSUFFICIENT`，继续观察。需要更长的确认，必须在查看任何相关确认结果之前另立协议。不能因为目标周期短而事后放宽边界。

### 可用天数

以截止日之后登记的有效交易日为上限。报告用独立正态近似给出检验 δ 所需的确认日数：

```
n_days ≈ ((z_{1-α} + z_{1-β}) × σ ÷ δ)²
```

σ 取各扰动配对日差标准差中最大的一个。可用天数不够时，报告写明"可用数据不足以检验 δ=…"，并给出当前数据可检验的最小 δ。这个公式只用于看量级；正式结论以区块模拟为准。

## 没有真实数据时

全部数据都是合成数据时，流程照常跑完，报告带 `FIXTURE_ONLY`，策略有效性为 `EVIDENCE_INSUFFICIENT`，短窗资格也是 `EVIDENCE_INSUFFICIENT`，并列出真实行情在字段、频率、时段和覆盖年限上的缺口。合成结果只用于验收，不可晋级。

## 假设

以下是本阶段新增的选择，都可以改。改动应发生在查看任何相关确认结果之前。

1. **开发段与向前验证段的分界是 2024-01-01。** 提示词包要求有向前验证段，没有规定边界。选 2024 全年作向前验证，是因为它紧挨截止日，约 250 个交易日。
2. **预热 20 个交易日不计入度量。** ADR 需要 10 个交易日，EMA、ATR 需要若干根 K；20 日留了余量。
3. **有效交易日 = RTH 完整且未降级。** 提示词包要求预登记有效日的定义，这里取最严的一种。夜盘缺数据不影响有效性。
4. **截止日之后的有效性由原始线的 RTH 覆盖判定。** 它与截止日之前的判定在数据相同时等价。
5. **`baseline_id` 不含 git commit。** 用源文件摘要代替，避免只改文档就让基线失效。
6. **滑点压力用解析计算，不重新回放。**
7. **风险规模结果是重算，不重新回放。**
8. **MAE／MFE 含出场所在子 K 的全幅。**
9. **四个扰动的选择。** 各取一个"砍掉一类入场"和一个"改时间窗"作 Track A，一个"放宽条件"和一个"改核心定义"作 Track B。
10. **功效模拟的平移假设。** 效应均匀加在每个交易日上，包括零交易日。真实的改动只会在有交易的日子产生差异，所以回撤条件和滑点压力条件的通过率是近似。
11. **各门槛预设**：家族 α 0.05、预登记 5 次正式检验、非劣效边界 0.05 R／日、δ 0.05 R／日、规划真实效应 0.10 R／日、回撤改善 10%、回撤增量 1 R、最低成交数 20 笔、区块 5 日。都在 `config/research.yaml`。
12. **资格取同一轨道各扰动中最差的通过率。** 保守。
13. **同一文件内内容冲突的重复 K 线**在两条摘要路径上处理不同（流式路径会计入，入库路径会排除）。真实数据里没有出现过这种情况。

## 已知问题

- **截止强平的交易带着多余的标记。** 回放时 15:55 那一步先于 15:55 的 1 分钟线到达，引擎先给仓位打上 `UNPRICEABLE`、`UNABLE_TO_FLATTEN` 并写一条严重告警，下一步行情到了才平仓，标记没有清掉。平仓价是对的（15:55 那根的开盘价再让 1 tick），盈亏不受影响。首次基线里有 47 笔这样的交易、108 条误报告警。问题在阶段 3 的引擎，本阶段没有改；修它会改变代码摘要，需要重新冻结基线。
- **并行跑扰动时偶发数据库锁。** 几个进程写同一个库，其中一个清理明细时别的可能等超时。已把等锁时间放宽到十分钟；仍失败时重跑 `baseline` 即可，已完成的回放会保留。
