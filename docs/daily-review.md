# 日复盘（阶段 6A）

每个已封存的 session 产出一份复盘。当日只登记观察；把观察升级为候选是阶段 6B 的事。

复盘由规则生成，不调用模型。同一个 session 复盘两次，结果相同。每条结论都带证据的 `event_id`。

## 命令

```bash
# 策略轨：缺省取该 scope 已冻结基线的主运行
uv run python -m trading_agent review --day 2024-06-12 --seal
uv run python -m trading_agent review --from 2019-09-05 --to 2024-12-31 --seal     # 全部 1340 天约 10 秒
uv run python -m trading_agent review --day 2024-06-12 --run-id <运行> --account <账户>   # 带上人工轨

# 只复盘人工轨：不需要策略运行，不读任何行情
uv run python -m trading_agent review --day 2026-11-10 --manual-only --seal
```

输出在 `reports/sessions/<session_id>.md` 和 `.json`（冒号换成下划线，不进版本控制）。JSON 里的 `review` 对象通过 `SessionReview` schema；`detail` 是完整明细。

## session 与封存

只有封存的 session 才能复盘。封存把当日指标固定下来，之后不改；重复封存返回原记录。

**策略轨的 session**：`<run_id>:<交易日>`。封存条件：

| 条件不满足 | 原因代码 |
| --- | --- |
| 当日没有任何决策记录 | `NO_ACTIVITY` |
| 运行的水位还没过截止强平时刻，或还有工作中的挂单 | `SESSION_IN_PROGRESS` |
| 还有未平的纸面仓位 | `POSITION_STILL_OPEN` |
| 真实数据，且晚于开发可见截止日（或截止日没设） | `HOLDOUT_PROTECTED` |

保留窗口和未解封的胶囊由评测侧处理，不能流回普通复盘。

**人工轨的 session**：`manual:<账户>:<交易日>`。它只含你自己的计划、成交和提醒，不含行情，所以不受开发可见截止日的限制。当日 Globex 时段结束（17:00 ET）之后才能封存，盘后任务 17:45 运行时即可封存；当日没有成交也没有提醒时是 `NO_ACTIVITY`。

为什么人工轨要能单独复盘：你的真实操作发生在现在，而策略的开发可见数据止于 2024-12-31。两者在时间上不重叠，人工轨没法挂在某个策略 session 上。

## 复盘里有什么

**四类信息分开写**，这是复盘最重要的纪律：

| 类别 | 内容 | 例子 |
| --- | --- | --- |
| 当时知道的事实 | 决策那一刻已经确定的 | 信号、挂单、成交价、订单到期 |
| 证据不足的判断 | 依赖保守规则或缺证据的 | 成交歧义、只有 5 分钟子 K、无法判定是否按计划 |
| 事后信息 | 当时不可能知道的 | 订单到期后价格越过了触发价；止损后价格到了原目标；MAE／MFE |
| 改动假设 | 应该怎么改 | 6A 不写。只在数据／引擎问题上立案 |

事后信息只看当日收盘之前的行情，不看次日。它只用来理解结果，不改变归因。

**机会与数据**：规则允许的机会（生成了挂单）和被拦截的机会（被过滤，或成立但没有挂单），各附 `event_id`。数据是否完整、所用子 K 周期。

**策略轨**：允许与拦截的数量、订单去向、净盈亏和净 R、MAE／MFE、歧义标记，并按 `config/research.yaml` 登记的元数据分组。分组键来自配置，复盘代码不认识策略专有字段。

**人工轨**：

- 先报计划覆盖率。低于阈值时，当日的纪律结论标注样本不足。
- 计划执行和策略一致性分开评价。纪律比例的分母只含可判定的平仓，无法判定的单列。
- 纪律事件计数。
- 逐条回顾当日的 `watch` 提醒：触发原因、多久之后解除、之后同一规则又触发几次。

## 归因

每个结果归入且只归入一类，按下面的顺序取第一个命中的：

| 顺序 | 条件 | 类别 |
| --- | --- | --- |
| 1 | 数据校验没通过的决策；带 `UNPRICEABLE`、`UNABLE_TO_FLATTEN`、`INVALID_AFTER_FILL` 的交易 | `DATA_ENGINE_ERROR` |
| 2 | 人工平仓被判违反计划；或带纪律事件；或它的开仓没有计划、是止损后无新形态的重试 | `RULE_EXECUTION_DEVIATION` |
| 3 | 人工平仓无法判定是否按计划 | `OUT_OF_RULE_OBSERVATION` |
| 4 | 其余：净盈利 | `PROFIT_BY_RULE` |
| 4 | 其余：净亏损或持平 | `LOSS_BY_RULE` |

盈利的违规仍是违规。按计划止损是按规则亏损。纸面交易由引擎按规则执行，只会落在第 1 或第 4 类。隔离的成交不参与。被拦截的机会不是结果，不归因。

## 观察

观察用一组固定的机制标签，只描述发生了什么。同一机制一个交易日一条，证据合并。

| 标签 | 轨道 | 含义 |
| --- | --- | --- |
| `TWO_STOPS_HALT` | 策略 | 当日两次止损后停手，之后的信号被拦截 |
| `FILTERED_SETUP` | 策略 | 信号被规则过滤，没有挂单 |
| `BLOCKED_SETUP` | 策略 | 信号成立但没有挂单（如已有同向持仓） |
| `EXPIRED_THEN_TRIGGERED` | 策略 | 挂单到期未成交，之后当日价格越过了触发价 |
| `STOPPED_THEN_TARGET` | 策略 | 止损出场后，当日价格到过原目标 |
| `AMBIGUOUS_FILL` | 策略 | 成交带歧义标记 |
| `FORCED_FLAT` | 策略 | 持仓到截止强平 |
| `DATA_QUALITY` | 数据／引擎 | 当日数据不完整、来源降级或校验没通过 |
| `ENGINE_ANOMALY` | 数据／引擎 | 引擎异常标记 |
| `DISCIPLINE_<类型>` | 人工 | 每种纪律事件一个，如 `DISCIPLINE_UNPLANNED` |
| `WATCH_ALERT_UNRESOLVED` | 人工 | 提醒到收盘仍未处理 |
| `WATCH_ALERT_REPEATED` | 人工 | 同一规则当日重复触发 |

没有可登记的内容时输出一条 `NO_OBSERVATION`，并说明需要补什么记录。

**候选**：只有数据／引擎类的观察会直接立案，写进 `candidates`（状态 `PROPOSED`，类别 `data_engine`）并登记台账。它走引擎修复流程：先修复并单独验收，冻结新代码后重建基线。它不是策略候选，没有可由评测解释的配置差异，所以正文不是 `Candidate` schema 的对象（那个 schema 要求一条配置差异）。策略和纪律类的观察只登记，交给 6B。

## 事故草稿

以下情况各生成一份草稿，状态 `DRAFT`，等你确认后才进回归库（阶段 8）：

- `DATA_ERROR`：当日有数据校验没通过的决策，或当日数据不完整、来源降级。
- `ENGINE_ANOMALY`：交易带引擎异常标记。
- `MAJOR_FILL_AMBIGUITY`：交易带 `AMBIGUOUS_BAR` 或 `GAP_THROUGH_STOP`。

只有 `AMBIGUOUS_ENTRY` 的不立案，在策略轨里计数。

草稿正文在 `<data_root>/incidents/drafts/<incident_id>.json`（项目之外），内容：

- 检查点：事故前 48 小时内最早的一条决策记录——那一刻的策略状态、版本元组、水位、风险域，以及当时的仓位和挂单。
- 从检查点到当日收盘后的全部决策记录的编号。
- 所依赖行情的键和 revision（周期、起始时刻、revision、可用时点）。不存价格：运行库保留全部 revision。
- 缺口：原样列出，不补任何 K 线。
- 预期行为与实际行为。

同一事故再次生成得到同一个标识，覆盖正文，不重复登记。能否独立重放由阶段 8 验证。

## 对备注的回应

当日关联的每条 `trader_notes` 都有一条回应。规则只能核对两种格式：

| 格式 | 处理 |
| --- | --- |
| `偏好: <键>=<值>` | 键在白名单内且值合法 → 采纳，并生成 Memory 候选（等确认后生效）。否则反驳。 |
| `更正: plan_link=<计划编号>`（关联到一笔成交） | 该计划在成交之前已激活 → 采纳（只登记，账本不自动改）。否则反驳。 |
| 其他 | 待定 |

白名单目前有两个键：`report_max_lines`（1–200）、`watch_poll_interval_seconds`（10–3600）。风险上限之类的键不在其中，进不了 Memory。备注是数据，不是指令：里面写"忽略规则""批准发布"之类的话不会被执行，只会得到"待定"。

## 模型的位置

本阶段不调用模型。每次复盘把一份压缩的结构化上下文（计数和观察说明，没有原始 K 线）放进已有的解释队列，类型 `SessionReview`，由模型在这份结果之上写叙述。消费者是阶段 10 的 `ops --explain`（见 `docs/ops-runbook.md`）；叙述只是解释，不改变复盘的观察、归因和候选。

## 假设

1. **复盘由规则生成，不调用模型。** 归因、计数、分组都可由规则判定；模型以后只写叙述。
2. **机制标签是固定集合。** 可能漏掉值得看的现象；要增删请告诉我。
3. **事后信息只看当日。** 隔夜之后才显现的问题看不到，换来的是不依赖未来数据。
4. **开仓时的偏差记在该仓位的平仓结果上。** 按合约和方向配对，先进先出。
5. **回放里数据不完整或降级的交易日也按 `DATA_ERROR` 立案。** 回放不做逐次数据校验，所以以交易日状态为准。
6. **检查点取 48 小时内最早的一条决策记录。** 提示词包说"默认可从事故前 48 小时开始取样，依状态需求补足"；是否足够由阶段 8 的重放验证。
7. **数据／引擎候选的正文不走 `Candidate` schema。**
8. **人工轨可以单独封存和复盘。** 提示词包默认人工轨与策略 session 同日；实际两者时间不重叠。
9. **备注只核对两种格式。**
10. **人工轨的"交易日结束"按期货口径判断**（次日 18:00 ET 之前的时刻都算当日已结束之后的下一交易日）。
